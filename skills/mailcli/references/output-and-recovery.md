# Output and recovery details

When a Mail-store profile was opened, every JSON envelope carries `data.store_profile` with `state`, `framework_version`, and `supported_framework_version`. `state:"unverified"` (with `code:"store_profile_unverified"`) means the store's framework stamp differs from the verified one while store version, minor version, UUID, and all required columns and indexes verified; reads still proceed, and human output prints one matching warning. Unsupported version, minor, UUID, or schema drift instead fails closed with `unsupported_mail_store_schema` and emits no profile.

Human `messages get` and `drafts open` details replace terminal controls with spaces; body LF/TAB and ordinary Unicode remain readable. JSON retains decoded values, body exports retain normalized content, and `messages raw`/raw exports retain exact MIME bytes. Use those explicit data paths when exact content is required.

Keep bodies, addresses, credentials, and attachment bytes out of logs and summaries unless requested. Detail commands default to metadata; use `--view plain|full`, `--fields`, or `--export /absolute/new/path` only when needed. Exports are complete, exclusive mode-0600 files with verified size and SHA-256; never accept truncation or infer missing bytes.

## Batch input

CLI JSON uses one encoder with HTML escaping disabled for envelopes, nested projections, pages, errors, and published command schemas. JSON control characters remain escaped. Before retaining concurrent batch-read bodies or headers, the CLI measures their encoded string sizes and sends only retain/drop decisions to the mail batch scheduler.

Use `mailcli batch --input - --json` with explicit refs and unique item IDs. Read the published `batch` schema for allowed operations, item fields, limits, and concurrency. Input is exactly one object up to 16 MiB; duplicate keys, case aliases, unknown fields, and trailing documents fail before dispatch. `move`/`copy` items take a `mailbox` destination ref; `move`/`delete` items may set `allow_draft_mutation`. A `delete` batch needs the `--confirm` flag and is refused without it; `--confirm` on any other operation is rejected. Results retain input order and per-item evidence, including `message_state` or `delete_result` on mutation items. No operation is retried automatically; never replay successful or uncertain mutation items. A read-batch `output_too_large` response permits replay only after following its correction guidance.

Batch JSON output is limited to 1 MiB by default; `--max-bytes` accepts values through 64 MiB for the complete envelope. Each read item accepts `view:"metadata"`, `view:"plain"`, or `view:"full"`, or a `fields` array from the published message field list. An omitted view preserves the CLI's legacy full-message behavior. The CLI measures requested body and header strings while concurrent reads are admitted. Read-batch overflow returns at most the first 10 item IDs and states in input order while retaining full total and outcome counts; it proves no effects, sets `retryability:user_input_required` and `replay_allowed:true`, and tells the caller to narrow `view`/`fields` or raise `--max-bytes` before replaying the same read batch. Mutation-batch overflow keeps effect-aware, non-replayable guidance and completed-effect evidence. Both return one bounded `output_too_large` envelope and never emit partial JSON. Every `output_too_large` envelope also carries `data.required_bytes`, `data.limit_bytes`, and `data.measured`; `exact` counts the complete successful envelope including its final newline, while batch read-content overflow reports the encoded body/header bytes as a `lower_bound` on the full response.

For agent batch reads, use metadata by default and request body fields only when needed:

```bash
printf '%s' '{"operation":"read","items":[{"id":"metadata","ref":"MESSAGE_REF","view":"metadata"},{"id":"body","ref":"MESSAGE_REF","view":"plain"},{"id":"selected","ref":"MESSAGE_REF","fields":["summary","content","content_complete"]}]}' | mailcli batch --input - --max-bytes 1048576 --json
```

Mutation results retain their `message_state`, `delete_result`, and `saved_attachment` evidence. A partial JSON batch reports `ok:false`, `batch_partial`, and exit code 1; check the envelope and every item's state regardless of exit status.

## Recovery details

`send_recovery_spool_changed` has separate unclaimed and accepted-send paths. A pre-submit `drafts.send` refusal includes `error.unclaimed_spool` only after the exclusive draft lease proves no send claim exists; it reports the absolute spool path, object type, owner UID, and four-digit octal mode from no-follow metadata. First run `drafts.inspect --ref REF --json` and confirm no retained claim. Remove only the reported path when the draft lock is free and its current metadata still matches; if it is a symlink, unlink only the link and never its target. SMTP was not contacted, and reporting removes nothing. An accepted-send failure has no `unclaimed_spool` evidence, keeps `effect_certainty:partial` and `retryability:observe_required`, and requires `drafts.reconcile --ref REF --json`; never delete its spool or replay SMTP.

Attachment saves are replayable only when the final output is proven absent and the cause is explicitly transient: cancellation or deadline, a Mail readiness failure proven before dispatch, or an IMAP connection/cancellation/disconnect/timeout or FETCH failure with a preserved network or truncation cause. TLS verification and input/configuration errors, missing or ambiguous attachments, and attachments not yet downloaded require correction. Known resource-limit, integrity, or deterministic-source failures require inspection without replay; unknown causes use `observe_required` and `inspect`. Complete, partial, or unknown publication outcomes always forbid replay while preserving verified `saved_attachment` evidence. A batch item's `retryable` value follows `error.guidance.replay_allowed`.

Read identity and source failures are non-replayable until corrected. For `invalid_reference`, obtain a current opaque ref from the matching MailCLI listing command; never edit a token manually. `ambiguous_reference` means a Mail.app account or mailbox path did not resolve uniquely; refresh the corresponding listing and retry with a current ref only after one target resolves. `stale_cursor` means the Mail.app page boundary changed or its prior offset disappeared; restart that listing without the stale cursor and continue with its fresh `next_cursor`. `account_reference_version_unsupported` means to use a compatible MailCLI build and preserve the local catalog entry; `account_reference_corrupt` and mixed `account_reference_invalid` are terminal inspection cases. `imap_message_uid_unknown` requires a refreshed catalog mapping or a fresh Message-ID-backed ref with verified mailbox UID. `imap_ambiguous_message_id` can stop read hydration; resolve the ambiguous message matches or refresh to a uniquely verified UID and UIDVALIDITY before retrying, and treat the diagnostic as identity resolution rather than mutation refusal. For `raw_source_partial`, finish the download in Mail.app or use a configured targeted IMAP source, then retry only with a verified complete source. `mail_busy`, `mail_automation_timeout`, and `mail_process_changed` prove the read was not dispatched or was a read-only probe, so retry is safe. Origin-ambiguous read failures such as `imap_mutation_failed`, `imap_sent_mailbox_not_found`, `mail_error`, `bridge_cleanup_failed`, `mail_automation_failed`, other doctor/probe failures, and internal `invalid_request` require inspection and must not be replayed. `mail_store_path_mismatch` and `content_export_changed` are terminal integrity errors: inspect the relevant identity and do not replay unchanged input. Preserved submission, mutation, APPEND, and partial-effect evidence always takes precedence.

`mail_access_gate_corrupt` is a pre-dispatch repair boundary. Quit Mail.app and retry the same existing operation while Mail is stopped; MailCLI clears only verified recovery-state contents under the exclusive lock and returns `mail_not_running` without dispatch. Reopen Mail.app and retry. If Mail is running or process lookup fails, the corrupt bytes remain untouched; lookup cancellation or timeout returns `mail_busy`. `mail_access_gate_unsafe` means no Mail.app action was dispatched; inspect the existing gate path's ownership, file type, link count, and identity, preserve the lock, and use a verified recovery plan before retrying. Never delete or replace `mail-access.lock`; the retained inode keeps waiting callers serialized.

Transport codes survive `fmt.Errorf` wrapping and `errors.Join`; an outcome-uncertain code wins over cleanup or rejection codes, so replay stays forbidden while `error.message` retains the joined diagnostics. If SMTP acceptance is followed by a local composed-reader close error, the acceptance evidence and cleanup diagnostic remain visible, the claim stays non-replayable, and no second SMTP submission is attempted.

`imap_resource_limit_exceeded` reports a bounded LIST or APPEND-continuation response overflow. Its JSON `error` includes `limit:{name,value}` and `observed_at_least`, a proven lower bound; byte limits report at least `limit.value + 1` when the exact overflow size is unavailable. The standalone overflow is terminal with no effect: inspect the bound and do not replay unchanged input. Existing partial-effect or outcome-uncertain guidance takes precedence and remains non-replayable.

Tagged IMAP `NO`/`BAD` failures include `error.imap_rejection` with the canonical command, status, nullable leading response-code atom, and complete tagged response text after control stripping and a 512-byte UTF-8 bound. Only a code at the start of tagged response text is interpreted. `imap_command_rejected` requires inspection and forbids unchanged replay; `NO [UNAVAILABLE]` on LIST, SEARCH, UID SEARCH, STATUS, or SELECT permits a safe read retry, while `BAD` is never automatically retryable. `NO [NONEXISTENT]` maps to `imap_mailbox_not_found` only for STATUS, SELECT, or APPEND; APPEND `NO [OVERQUOTA]` maps to `imap_quota_exceeded`. LOGIN `NO` retains `imap_auth_failed`; LOGIN `BAD` is generic. Once SMTP has accepted a message, any IMAP mirror rejection requires `drafts.reconcile`, never another `drafts.send`.

Read failures are replayable only for explicitly classified transient errors. Input or configuration failures require correction, terminal failures require inspection, and unknown read failures use `retryability:observe_required` with `recovery.action:inspect`. Mail-store, account and Mail.app access/readiness failures require user action: follow `recovery.instruction` to grant Full Disk Access, correct the account or binding, grant Mail Automation, or recover Mail.app safely. Never delete or replace the MailCLI access-gate file.

Permission failures retain their cause through draft-state and mailbox-cache wrappers and require access correction, with no effect and no unchanged replay; malformed state remains terminal/inspect. Certificate trust and hostname verification failures retain `imap_connect_failed` but require correcting IMAP TLS configuration; never disable verification. Connection refusal, disconnect and timeout remain transient. `imap_fetch_failed` permits replay only with a preserved network or truncated-connection cause; deterministic invalid sources and FETCH rejections require inspection. Hydration and CLI output retain that policy with sanitized diagnostics, and outcome uncertainty always forbids replay.

For `messages.mark`, `messages.move`, `messages.copy`, and `messages.delete`, and for those operations inside `batch`, `imap_ambiguous_mailbox` is a pre-dispatch correction: no mutation command was sent, replay is forbidden until correction, and the recovery instruction tells you to correct the conflicting mailbox identities by renaming a colliding server mailbox or correcting duplicate special-use assignments, then refresh the mailbox list and rerun only after the requested mailbox resolves uniquely. A wrapped outcome-uncertain error remains uncertain and must be inspected.

A definite `messages.get` `not_found` means the read found no message for that ref. No effect occurred, but retrying the same ref cannot make progress. Follow `retryability:user_input_required`, `replay_allowed:false`, and `recovery.action:correct` by obtaining a fresh valid ref before another lookup. Transient read failures retain their safe retry guidance.

`output_too_large` can follow `messages.get`, `messages.raw`, `attachments.list`, `drafts.open`, `drafts.inspect`, a projected draft response, or `batch`. For a read batch, inspect `data.required_bytes`, `data.limit_bytes`, and `data.measured`, narrow `view`/`fields` or raise `--max-bytes`, then replay the same read request; no effect occurred. The failure envelope includes at most the first 10 item IDs and states in input order plus full total and outcome counts. Mutation batches retain effect-aware guidance and completed-effect evidence; never replay without inspecting the retained result. `exact` is the complete successful envelope size including the terminating newline; `lower_bound` is the encoded requested batch body/header bytes and is guaranteed above the configured limit. An oversized `drafts list` uses `error.guidance.recovery` to offer a half-sized page while retaining the cursor, selected fields, and any explicit `--max-bytes`; at limit 1 it has no smaller-page command. A completed draft mutation has `effect_certainty:complete`, `replay_allowed:false`, and a `drafts.inspect` recovery command only when the draft ref is retained. Other projection failures omit a command because the error does not retain the original invocation arguments. `draft_revision_conflict` from `drafts.update`, `drafts.send`, or `drafts.reconcile` emits `drafts.inspect` with the retained ref; if it is absent, inspect remains the action and command/args stay empty.

`draft_busy` comes from a lease-backed draft operation and means this invocation did not acquire the draft lease or change that draft. It requires observation and forbids replay. With a retained ref, `retryability:observe_required` pairs with `recovery.action:inspect` and the runnable `drafts.inspect --ref REF --json`; that inspection does not acquire the competing mutation lease. Without a ref, recovery stays `observe` and has no command. Never replay a send until you inspect the competing draft state. Revision conflicts and completed draft mutations use `drafts.inspect --ref REF --view full --json` when a ref is retained, because they need the complete content to resolve or review the result; state-only recovery uses the default plain view. `search_cursor_stale` and `search_index_changed` come from `messages.search` and `messages.filter`; a stale cursor requires correction by removing the cursor, while an index change permits a safe read retry. Neither search error retains the original filters, so neither emits a complete command. Read-only `account_binding_stale` requires inspecting `accounts.list --json` and correcting the binding to an enabled account through `send setup` before retry. Effectful `drafts.send` or IMAP sender-alias resolution retains observation via `accounts.list --json`, without copying account identifiers or credentials into recovery args. `mail_recovery_required` from Mail.app-gated operations such as `drafts.handoff` requires quitting and reopening Mail.app; no CLI command can safely perform that recovery.

`smtp_data_incomplete` proves SMTP failed before its end-of-data terminator was attempted; the claim is cleared and an explicit send retry is safe. `imap_append_incomplete` proves APPEND failed before its terminating CRLF; the session is discarded. During `drafts send`, SMTP has already accepted the message, so the retained result is mirror-pending and recovery must reconcile without resubmitting SMTP; during `drafts reconcile`, Sent is searched before the known-incomplete APPEND is retried. For `smtp_submission_unknown`, `sent_mirror_pending`, `imap_append_outcome_unknown`, `imap_copy_outcome_unknown`, and `imap_move_outcome_unknown`, retain the operation ID and follow the emitted recovery command. A send attempt points to `drafts reconcile --ref DRAFT_REF --json`; a retained visible-compose attempt points to `drafts handoff-reconcile --ref DRAFT_REF --attempt ATTEMPT_ID --outcome opened|failed --confirm --json`; partial hydration points to `messages get --ref MESSAGE_REF --json` or `drafts open --ref MESSAGE_REF --json`. Never blindly retry an outcome-unknown operation.
