# Installation, setup, and diagnostics

Before running a downloaded release installer, follow the README bootstrap path: use an independently trusted OpenSSL 3 binary to verify the pinned Ed25519 signature over the exact `SHA256SUMS` bytes and the expected archive digest before extraction or `install.sh` execution. Never run a downloaded installer before both checks succeed.

1. To install from a source checkout, run `scripts/build/install-local.sh [BINARY_DESTINATION]`. It builds the current binary and invokes the shared rollback-safe installer, which stages and publishes the matching binary and `skills/mailcli` together. The binary destination defaults to `~/.local/bin/mailcli`; set `MAILCLI_SKILL_DESTINATION` to redirect the skill. After installation, start a new agent session so the skill is discovered, then request the needed scoped capabilities for the installed executable. Checkout-only helper `scripts/utils/mailcli-preflight.sh capabilities --binary PATH` can cache the full catalog; add `--for ID,ID,...` for a selected workflow. Selected caches use the executable SHA-256, schema, and normalized command set, and retain the selected envelope without expanding it to the full catalog. The cache is mode 0600 and stores only valid `ok:true` JSON. A cache hit avoids another capabilities call; `--refresh` refreshes the current selection, while `invalidate` clears full and selected entries for that binary/schema. If the helper is unavailable, request the needed scoped capabilities once for the current binary and retain that result for the current session; do not trust an older result.

2. In a source checkout, check an existing user skill only with `scripts/tests/report-skill-drift.sh`. It is read-only; pass `--repository PATH --installed PATH` for explicit inputs. `status=match` is current, while `missing`, `mismatch`, or `unstable` includes reconciliation guidance and never installs anything.

Local discovery is host-specific: Codex loads the default `~/.agents/skills/mailcli`; Claude Code loads `~/.claude/skills/mailcli` and supports a symlink to the default installation. After a verified default install, create that link only if the Claude entry is absent; inspect existing entries instead of replacing them. The link follows canonical updates without a second skill copy. Direct source/release installers may instead use `MAILCLI_SKILL_DESTINATION="$HOME/.claude/skills/mailcli"`, but self-update ignores this override: refresh a separate copy through its original installer with the same destination. Other hosts and cloud sessions require their own documented loading path; do not assume they discover either local folder.

For Gmail and iCloud, configure the sender with `mailcli send setup --from ALIAS [--account ACCOUNT_REF] --json`. For another domain, first resolve its stable account ref, then use `mailcli send setup --account ACCOUNT_REF --from ALIAS --smtp-host HOST --smtp-port PORT --imap-host HOST --imap-port PORT --json`. An optional `--credential-account LOGIN` selects the credential identity for that binding. MailCLI validates explicit public endpoints before prompting for or storing a credential; do not guess hosts or ask for the password in chat. Reuse the exact account and alias from `accounts list`, and follow the scoped `send.setup` schema.

The built-in Gmail and iCloud transports currently use app-specific passwords; MailCLI does not implement Sign in with Google or Apple Account authorization. Google requires 2-Step Verification for app passwords and may withhold them from organization-managed or Advanced Protection accounts. Apple app-specific passwords require two-factor authentication. Provider account settings can therefore prevent setup even when an address is in the supported provider list.

Credential caches invalidate immediately after successful Keychain storage, including when later publication fails. If `send.setup` subsequently fails, `data.partial_effects` reports `keychain_store:complete`, then `binding_publish:none|unknown|complete`, and optionally `lock_release:failed`. `unknown` means rename happened but directory sync or identity verification failed; `complete` remains complete despite a later lock-release warning. An implicit credential or endpoint change during password entry returns `account_binding_changed`, `binding_publish:none`, `retryability:user_input_required`, and no replay. Explicit flags win; unchanged implicit fields come from the locked document. Follow `error.guidance.recovery` to the read-only `mailcli accounts list --json`, inspect the binding, then make an explicit setup decision. MailCLI never retries the binding update or rolls back the Keychain credential automatically. Validation and Keychain storage failures retain no-effect guidance.

Binding writers acquire the legacy lock before the new lock. The standard basename uses `account-bindings.lock`; custom basenames use `account-bindings-<full lowercase SHA256 of basename>.lock` in their pinned parent. Both inodes remain retained for mixed-version waiters; never unlink an unlocked binding lock. Different custom binding owners remain independent.

`mailcli version --json` reads the installed identity. `mailcli update --json` checks the signed release and installs a verified binary and matching skill; use it only when the user requested an update, then refresh the executable identity and capability contract.

For an authorized upgrade through an older updater or installer that assumes plain version output, use `MAILCLI_OUTPUT=human mailcli update` or `MAILCLI_OUTPUT=human /absolute/path/install.sh`. Old binaries ignore the setting; new binaries honor it in inherited version probes. Current installers and updaters select the compatible probe format explicitly.

If an update error follows an installation attempt, `data.update_result` reports the binary path, target `latest_version`, `updated`, and `failed_phase`; `error.guidance.effect_certainty` is `complete` only when installed-version verification succeeded, otherwise `unknown`. Follow the read-only `mailcli version --json` recovery command and inspect the installed identity before another update decision. Do not rerun the installer automatically or assume that it rolled back.

All installation entrypoints share `~/Library/Application Support/MailCLI/update.lock` through recovery, verification, and cleanup. Direct installers wait at most 30 seconds; self-update uses its command deadline and passes ownership to the child. Self-update ignores `MAILCLI_INSTALL_PACKAGE_ROOT` and uses its authenticated package; source installation retains its explicit checkout override. Never unlink or steal this lock or infer abandonment from age. If identity checks refuse recovery, retain the transaction and replaced artifacts for inspection. Cancel automated installers through their whole process group.

Respect the published provider set, `raw_mime_send`, `send_transport`, `mutation_transport`, page/batch limits, and IMAP pool limits. LIST/STATUS/SEARCH/FETCH share the account pool; APPEND and mutations are exclusive per account.
